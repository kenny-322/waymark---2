# WAY●MARK — архитектура системы городов

## Зачем нужен этот документ

Этот документ фиксирует структуру каталога городов, профилей городов и мест для подробной векторной карты. Он обновлён для WAY●MARK 1.32.

**Важно:** текущий сайт не переведён на новую структуру автоматически. Текущие файлы и формат `city-data.js` сохранены, поэтому интерфейс не должен измениться из-за этого документа. JSON-схемы в папке `schemas/` описывают целевой формат для постепенного внедрения.

## Что уже есть в WAY●MARK 1.32

- `city-data.js` — отдельный каталог `CITY_DATA`.
- `script.js` — поиск, выбор городов, маркеры и подписи глобуса, карточки и построение маршрутов.
- `transport-data.js` — отдельные данные транспортных связей.
- У городов уже есть `id`, название, страна, флаг, координаты, популярность, часовой пояс, валюта, язык, описание, шесть достопримечательностей, климат, кухня и демонстрационные погодные поля.
- Логика поиска и маршрутов использует `id` города; уровень видимости на глобусе зависит от `popularity`.
- При дальнем масштабе асинхронно загружаются границы стран из GeoJSON Natural Earth; подписи стран плавно уступают место подписям городов по мере приближения.
- Карта города реализована как отдельный режим на `MapLibre GL JS` с векторным стилем OpenFreeMap. Она создаётся только после выбора действия «Исследовать город».
- Места в радиусе выбранного города загружаются по запросу из OpenStreetMap через Overpass API. Поэтому для новых городов не нужен ручной список координат POI, если данные доступны в OpenStreetMap.
- В городском исследовании можно выбрать места и менять их порядок. Текущая линия — только черновая схема посещения, не навигация по улицам. Для реальных пешеходных, автомобильных и общественно-транспортных путей необходим отдельный маршрутизатор.

Проверка текущего каталога: **215 городов, 104 различных значения поля `country`, повторяющихся `id` и координат с точностью до 4 знаков не найдено, у каждого города есть 6 достопримечательностей и ожидаемые обязательные поля**. Это проверка структуры, а не независимая проверка истинности каждого описания или координат.

## Целевая архитектура

### 1. Индекс городов — лёгкие данные для глобуса

Индекс содержит только то, что нужно для поиска, отображения точек и перехода к городу:

- неизменяемый `id`;
- название;
- страна и её ISO-код;
- широта и долгота;
- важность/популярность для отображения на разных уровнях масштаба;
- путь к подробному профилю.

Будущий файл может называться `data/cities/index.json`. Не обязательно создавать его сразу: это цель миграции, когда мы подготовим совместимый переход с текущего `CITY_DATA`.

### 2. Профиль города — подгружается по необходимости

Профиль содержит описание, язык или языки, валюту, часовой пояс, климат, сезонность, кухню и список основных достопримечательностей. В будущем профили можно хранить отдельно, например `data/cities/details/ru-moscow.json`.

Текущий сайт ожидает некоторые поля в старом формате (`language` как строку и `attractions` как массив пар `[название, описание]`). Поэтому при миграции надо либо оставить эти поля до окончания перехода, либо добавить адаптер, который преобразует новый формат в старый для компонентов интерфейса. Нельзя менять структуру вслепую.

### 3. Места внутри города — отдельный каталог

Места для подробной городской карты не следует смешивать с индексом городов. Каждое место должно иметь стабильный `id`, `cityId`, название, категорию и координаты. Описание, адрес, сайт, часы работы и источник данных могут быть дополнительными полями.

Например, Красная площадь будет отдельным объектом места, связанным с `cityId: "moscow"`. У неё будут собственные координаты. Благодаря этому один город может иметь много тысяч точек, а глобусу по-прежнему нужны только компактные данные городов.

### 4. Границы стран и уличная карта — не каталог городов

Границы стран, дороги, здания, парки и прочие географические объекты должны поступать из отдельного картографического источника или векторных тайлов. Не нужно вручную хранить геометрию каждой улицы внутри профиля города.

Каталог городов отвечает за выбор города и связь с профилем. Картографический движок отвечает за отображение базовой карты. Каталог мест отвечает за POI (точки интереса), выбранные пользователем и специальные маршруты WAY●MARK.

## Правила стабильности

1. **Не переименовывать `id` уже существующего города без миграции.** Маршруты, транспортные связи и сохранённые в браузере путешествия могут ссылаться на эти идентификаторы.
2. Для новых записей выбирать уникальный и читаемый ID. В целевой схеме предпочтителен ID с кодом страны, например `jp-kyoto`; текущие ID (`moscow`, `paris` и т. п.) сохраняются ради обратной совместимости.
3. Координаты задавать числами в десятичных градусах: `lat` от -90 до 90, `lon` от -180 до 180.
4. Код страны хранить отдельным полем (`countryCode`), а название страны — отдельным (`countryName`). Название нельзя использовать как постоянный ключ: варианты написания и локализация могут меняться.
5. Не придумывать текущую погоду, цены, расписания или часы работы. Если данные демонстрационные или неизвестны, это должно быть явно обозначено.
6. Данные из новых внешних источников должны проходить проверку лицензии, обязательных атрибуций, качества и допустимых способов использования.
7. Для большого каталога применять уровни детализации: на дальнем масштабе — страны и небольшое число городов, при приближении — больше городов, на карте города — только места в видимой области.

## План постепенного внедрения

1. Зафиксировать текущую версию и запускать проверку каталога перед дальнейшими изменениями.
2. Добавить к данным страновые коды и нормализовать модель без смены старых `id`.
3. Создать индекс городов и профили отдельно, сохранив совместимость со старым интерфейсом через адаптер.
4. Добавить слой мест (POI) и одну пилотную карту Москвы.
5. Проверить выбор города, поиск, маршруты, транспорт, сохранённые путешествия и мобильную версию.
6. Только после тестов постепенно расширять каталог и интеграцию подробной карты.

## Файлы в этом комплекте

- `schemas/city-index.schema.json` — целевой формат индекса городов.
- `schemas/city-profile.schema.json` — целевой формат подробного профиля.
- `schemas/city-place.schema.json` — формат места внутри города.
- `schemas/city-route.schema.json` — формат черновика городского маршрута с будущими режимами передвижения.
- `city-explorer.js` — универсальное исследование города, загрузка мест и список остановок.
- `country-overlay.js` — векторный слой границ и подписей стран для глобуса.
- `scripts/validate-city-data.mjs` — проверка текущего каталога `city-data.js`.

Запустить проверку из корня проекта:

```bash
node scripts/validate-city-data.mjs
```

На текущем этапе этот скрипт проверяет старый `CITY_DATA`, чтобы служить регрессионной проверкой во время будущей миграции. Он не заменяет проверку фактической достоверности данных.
